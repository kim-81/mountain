# HTTPS 서버 연결 준비 · 아직 공개 배포하지 않음

이 문서는 향후 서버 운영 담당자를 위한 설정 설명입니다. 서버·도메인 계약이나 외부 공개는 하지 않았습니다. 기존 로컬 미리보기는 별도 설정 없이 유지됩니다.

## 구성

사용자 브라우저 → HTTPS를 처리하는 운영 환경/리버스 프록시 → 같은 서버의 `127.0.0.1:4173` Node 앱 → 지속 저장소의 SQLite.

기본 설정은 외부로 직접 HTTP를 열지 않습니다. HTTPS를 제공하는 운영 환경이 앞에서 요청을 전달해야 합니다. 별도의 프록시 프로그램을 설치하지 않았습니다. 운영 환경을 선택할 때 HTTPS와 지속 디스크, Node.js 24 이상 지원이 필요합니다.

| 환경 변수 | 기본값 | 설명 |
|---|---|---|
| SANGIL_PUBLIC_ORIGIN | 없음 | 예: https://trail.example.com. 실제 주소로 교체. 경로·끝 슬래시 제외 |
| SANGIL_PORT | 4173 | 앱의 루프백 수신 포트 |
| SANGIL_LISTEN_HOST | 127.0.0.1 | 컨테이너 호스팅의 HTTPS 프록시가 필요로 할 때만 0.0.0.0. 공개 원점 지정 필수 |
| SANGIL_DATA_DIR | 프로젝트/.local-data | SQLite가 보관될 지속 저장소의 절대 경로 |

PowerShell 설정 예시(주소와 디렉터리를 실제 운영 값으로 바꾼 뒤 사용):

```powershell
$env:SANGIL_PUBLIC_ORIGIN = 'https://trail.example.com'
$env:SANGIL_PORT = '4173'
$env:SANGIL_DATA_DIR = 'D:\sangil-data'
node scripts/serve.mjs
```

프록시는 원래 Host를 보존하거나 `127.0.0.1:4173`으로 전달해야 합니다. Origin 헤더를 변경하면 안 됩니다. `X-Forwarded-Proto` 등 임의 전달 헤더로 인증 원점이나 Secure 속성을 바꾸지 않습니다. 명시한 공개 원점으로 판단합니다. 프록시 뒤에서는 모든 요청이 같은 주소로 보이므로 로그인 제한(분당 20회)은 보수적으로 합산됩니다. 운영 규모에 맞는 신뢰 프록시·이용자별 제한은 추가 구현 대상입니다.

## 공개 전 확인

- HTTPS 도메인에서 가입·로그인·로그아웃·비밀번호 변경·탈퇴가 동작하고 Secure/HttpOnly/SameSite 쿠키가 적용되는지 확인.
- 다른 출처에서 일정/계정 변경 요청이 거부되는지 확인.
- 운영 DB에 예시 계정과 테스트 사진이 남지 않도록 별도 데이터 폴더를 사용.
- 서버 종료 후 DB와 WAL 자료를 일관되게 백업하고 복구 검증. 실행 중 DB 파일 하나만 복사하는 방식은 피함.
- 서버 재시작·지속 디스크·접근 권한·백업·오류 감시·서비스 운영 정책 준비.

## 네이티브 연결은 별도 단계

이 설정만으로 Android/iOS 계정이 연결되지 않습니다. 네이티브 앱은 로컬 화면을 사용하고 인증은 현재 동일 출처 쿠키 방식입니다. 실제 HTTPS 주소가 정해지면 네이티브 인증 전달/보관, 연결 실패 시 기기 저장 모드, 기존 기기 자료의 서버 이전 여부를 구현·검증해야 합니다. 임의의 서버 주소를 입력하는 UI는 제공하지 않습니다.
